# Module Authoring Guide

This guide explains how to write a `.gmod` file — the primary authoring artifact in graydr. Read it
top-to-bottom to produce a working module without consulting source code.

---

## Overview

A **module** is a self-contained unit of IaC (Infrastructure as Code) that encapsulates provider-specific
code behind a stable interface. One module can emit Terraform HCL for AWS, Bicep for Azure, and
CloudFormation YAML for GCP — the caller never sees the provider-specific code, only the module's declared
inputs and outputs.

When to write a module:

- You have IaC code that varies by cloud provider and want to deploy the same logical resource across providers.
- You have IaC that is reused across multiple templates (e.g., an S3 bucket definition used in three different
  templates).
- You want to attach governance metadata (security tier, compliance frameworks) to an infrastructure unit so
  that metadata flows into the compiled output.

When NOT to write a module: if the IaC is truly one-provider-only and will never be reused, putting it
directly in a template's resource block is simpler.

## Quickstart: Your First Module

Generate a starter module with the `init` subcommand:

```
graydr init module --output my_module.gmod
```

This writes a valid `.gmod` scaffold to `my_module.gmod`:

```hcl
# Generated by `graydr init module`
# See the Module Authoring Guide for complete documentation.
module "my_module" {
  metadata {
    description = "TODO: describe what this module does"
    version     = "0.1.0"
  }

  interface {
    inputs {
      my_variable = {
        required  = true
        sensitive = false
      }
    }
    outputs {
    }
  }

  validation {
  }

  generate {
    case "provider" {
      aws {
        code = <<-EOT
          # TODO: write Terraform/CloudFormation HCL here
          # Use $my_variable for graydr variables
        EOT
        outputs {
        }
      }
      azure {
        code = <<-EOT
          # TODO: write Bicep/ARM HCL here
        EOT
        outputs {
        }
      }
    }
  }
}
```

Replace the `TODO` placeholders with real values and run:

```
graydr validate my_module.gmod
```

Exit code 0 means the module is structurally valid.

## File Structure

Every `.gmod` file has the following top-level structure:

```hcl
module "name" {
  metadata   { ... }
  interface  { ... }
  validation { ... }
  generate   { ... }
}
```

All four blocks are required. The `module` keyword is followed by a string label — the module name.
Module names are referenced by templates in their `module = "name"` resource declarations.

---

## Metadata Block

The metadata block carries descriptive and governance information about the module.

```hcl
metadata {
  description            = "Cross-cloud object storage module"
  version                = "0.1.0"
  security_tier          = "high"
  compliance_frameworks  = "SOC2,PCI-DSS"
  cost_tier              = "premium"
  data_classification    = "confidential"
  disaster_recovery_tier = "tier1"
  approval_required      = true
}
```

Fields:

| Field                    | Required | Type    | Description                                          |
|--------------------------|----------|---------|------------------------------------------------------|
| `description`            | Yes (for community docs) | string | Human-readable description of what the module does |
| `version`                | No       | string  | Semantic version string                              |
| `security_tier`          | No       | string  | Security classification (e.g., `"high"`, `"low"`)   |
| `compliance_frameworks`  | No       | string  | Comma-separated compliance tags (e.g., `"SOC2,PCI-DSS"`) |
| `cost_tier`              | No       | string  | Cost profile (e.g., `"premium"`, `"standard"`)      |
| `data_classification`    | No       | string  | Data sensitivity level                               |
| `disaster_recovery_tier` | No       | string  | DR tier (e.g., `"tier1"`, `"tier2"`)                |
| `approval_required`      | No       | bool    | Whether this module requires change-management approval |

Governance fields are written into the compiled output as a comment block so downstream reviewers can
inspect them without reading the source module:

```
# graydr governance metadata
# security_tier: high
# compliance_frameworks: SOC2,PCI-DSS
# cost_tier: premium
# data_classification: confidential
# disaster_recovery_tier: tier1
# approval_required: true
```

## Interface Block

The interface declares what the module accepts as inputs and what it exposes as outputs.

### Inputs

```hcl
interface {
  inputs {
    bucket_name = {
      required  = true
      sensitive = false
    }
    region = {
      required  = true
      sensitive = false
    }
  }
  outputs {
    bucket_url = {}
  }
}
```

Each input is an identifier followed by an attribute map. Supported attributes:

| Attribute   | Type   | Description                                                   |
|-------------|--------|---------------------------------------------------------------|
| `required`  | bool   | If `true`, compilation fails when no value is supplied        |
| `sensitive` | bool   | If `true`, the value is masked in log output                  |
| `default`   | string | Value used when no override is provided                       |

**Required sensitive input** (API key pattern):

```hcl
api_key = {
  required  = true
  sensitive = true
}
```

**Optional input with default:**

```hcl
region = {
  required  = false
  sensitive = false
  default   = "us-east-1"
}
```

**Dotted-path input** (parameter group access):

```hcl
primary_db.size = {
  required  = true
  sensitive = false
}
```

Dotted-path inputs are populated from parameter groups declared in the consuming template. The
value of `primary_db.size` comes from the `primary_db { size = {} }` parameter group.

### Outputs

The `outputs {}` block in the interface declares what output names this module can expose. The actual
output values are defined inside each case arm's `outputs {}` block. The interface-level declaration
is the public contract — it tells consuming templates what names to reference.

```hcl
outputs {
  bucket_url = {}
}
```

## Validation Block

The validation block contains rules that run before code generation. Each rule is a named condition with
an error message and a severity level.

```hcl
validation {
  rule "bucket_name_length" {
    condition     = "$bucket_name != \"\""
    error_message = "bucket_name must not be empty"
    severity      = "error"
  }
}
```

Rule fields:

| Field           | Description                                                           |
|-----------------|-----------------------------------------------------------------------|
| `condition`     | An expression (evalexpr syntax). `$variable_name` references are stripped of the `$` sigil before evaluation. A condition that evaluates to `true` means the rule **passes**. |
| `error_message` | Human-readable message shown when the condition evaluates to `false`. |
| `severity`      | One of `"error"`, `"warning"`, or `"info"`.                          |

**Severity levels:**

- `"error"` — Aborts compilation. The module cannot be used until the condition is satisfied.
- `"warning"` — Emits a warning and continues compilation. The output is still produced.
- `"info"` — Informational only. Always emits the message regardless of condition value (treat condition as
  context).

**Example with each severity:**

```hcl
validation {
  rule "bucket_name_not_empty" {
    condition     = "$bucket_name != \"\""
    error_message = "bucket_name must not be empty"
    severity      = "error"
  }

  rule "region_is_recommended" {
    condition     = "$region == \"us-east-1\""
    error_message = "Consider using us-east-1 for lower latency"
    severity      = "warning"
  }

  rule "cost_info" {
    condition     = "true"
    error_message = "This module uses premium storage pricing"
    severity      = "info"
  }
}
```

The `condition` expression uses the evalexpr crate's syntax. Variable names in conditions are written
with the `$` sigil (e.g., `$bucket_name`), which is stripped before evaluation so the expression engine
sees bare identifiers.

## Generate Block and Case Arms

The `generate` block contains one or more `case` blocks. Each `case` block dispatches on one or more
variable values to select the appropriate IaC code to emit.

### Single-Variable Case

The simplest form dispatches on a single variable:

```hcl
generate {
  case "provider" {
    aws {
      code = <<-EOT
        resource "aws_s3_bucket" "$bucket_name" {
          bucket = "$bucket_name"
          region = "${var.region}"
        }
      EOT
      outputs {
        bucket_url = "${aws_s3_bucket.storage.bucket_regional_domain_name}"
      }
    }
    azure {
      code = <<-EOT
        resource "azurerm_storage_account" "$bucket_name" {
          name     = "$bucket_name"
          location = "$region"
        }
      EOT
      outputs {
        bucket_url = "${azurerm_storage_account.storage.primary_blob_endpoint}"
      }
    }
  }
}
```

The `case "provider"` block selects the arm whose identifier matches the resolved value of the
`provider` variable at compile time. If `provider = "aws"`, the `aws { ... }` arm is selected.

**Variable substitution in code blocks:**

- `$bucket_name` — a graydr variable. The dollar sign triggers substitution: graydr replaces this
  with the resolved value of `bucket_name` before passing the code to the IaC toolchain.
- `${var.region}` — Terraform-native interpolation. The `${...}` form is **not** a graydr variable.
  graydr passes it through unchanged to the IaC toolchain.
- `${aws_s3_bucket.storage.bucket_regional_domain_name}` in `outputs {}` — an output reference
  template string. This is also passed through; graydr uses it as a template that resolves to the
  actual Terraform resource attribute reference for the resource instance name used in the template.

The distinction is important: `$variable_name` (bare dollar, no braces) is a graydr variable. `${...}`
(dollar with braces) is IaC-native interpolation that graydr does not touch.

### Multi-Variable Case

When code must vary by more than one dimension, use the multi-variable form:

```hcl
generate {
  case "provider" "engine" {
    arm "aws" "aurora" {
      code = <<-EOT
        # AWS Aurora-specific Terraform
      EOT
      outputs {}
    }
    arm "azure" "sqlserver" {
      code = <<-EOT
        # Azure SQL Server Bicep
      EOT
      outputs {}
    }
  }
}
```

**This syntax is non-obvious — read this section carefully.**

In the multi-variable form, the block identifier MUST be `arm` and the variable values are **string
labels** that follow it. So `arm "aws" "aurora"` is an HCL block with identifier `arm` and two
string labels: `aws` and `aurora`.

Why `arm` instead of just the value? HCL block bodies require identifier attribute keys — quoted
strings cannot be used directly as block identifiers. The `arm "aws" "aurora"` pattern is: identifier
(`arm`) + string labels (`"aws"`, `"aurora"`). This is the valid HCL form.

The single-variable shorthand (`aws { ... }`) is the backward-compatible degenerate case where the
identifier itself is the value (no string labels needed for one variable).

**Match rules for multi-variable case:**

- The compiler zips the variable list with the arm labels: `provider` matches `"aws"`, `engine`
  matches `"aurora"`.
- All values must match simultaneously for an arm to be selected.
- If no arm matches all values, it is a hard compile error.

### Case Completeness

If a properties file contains a value for a case variable that has no matching arm, graydr emits a
warning. If the resolved value at compile time has no matching arm at all, graydr emits a hard error
and stops compilation.

Example: `case "provider"` has arms for `aws` and `azure`. If `provider = "gcp"` is supplied at
compile time, compilation fails with `NoMatchingArm`.

## Output Reference Template Strings

The `outputs {}` block inside each case arm maps output names to template strings. The template strings
use the `${resource_reference}` syntax to capture the IaC-native reference expression for the
specific resource instance name used in the template.

```hcl
outputs {
  bucket_url = "${aws_s3_bucket.storage.bucket_regional_domain_name}"
}
```

When a template compiles resource `main_storage` using the `storage` module, graydr replaces the
resource name placeholder in the template string with `main_storage` to produce the consuming
resource's input value.

This injection happens at the `gtpl_override` layer of the variable resolution chain, so CLI flags
(`-D`) can still override output-injected values if needed.

## Complete Example

The following is `tests/fixtures/sample.gmod` — the canonical reference module used throughout the
test suite. Every piece of syntax shown in this guide comes from this file.

```hcl
module "storage" {
  metadata {
    description = "Cross-cloud object storage module"
    version     = "0.1.0"
  }

  interface {
    inputs {
      bucket_name = {
        required  = true
        sensitive = false
      }
      region = {
        required = true
        sensitive = false
      }
    }
    outputs {
      bucket_url = {}
    }
  }

  validation {
    rule "bucket_name_length" {
      condition     = "$bucket_name != \"\""
      error_message = "bucket_name must not be empty"
      severity      = "error"
    }
  }

  generate {
    case "provider" {
      aws {
        code = <<-EOT
          resource "aws_s3_bucket" "$bucket_name" {
            bucket = "$bucket_name"
            region = "${var.region}"
          }
        EOT
        outputs {
          bucket_url = "${aws_s3_bucket.storage.bucket_regional_domain_name}"
        }
      }
      azure {
        code = <<-EOT
          resource "azurerm_storage_account" "$bucket_name" {
            name     = "$bucket_name"
            location = "$region"
          }
        EOT
        outputs {
          bucket_url = "${azurerm_storage_account.storage.primary_blob_endpoint}"
        }
      }
    }
  }
}
```

Annotations:

- `module "storage"` — the module name. Templates reference this with `module = "storage"`.
- `interface.inputs.bucket_name` — required input, not sensitive. Must be supplied by the template
  or properties file.
- `interface.outputs.bucket_url = {}` — declares that this module exposes `bucket_url` as an output.
  The actual value is set per-arm in `generate`.
- `validation.rule "bucket_name_length"` — condition uses `$bucket_name`, evalexpr strips the `$` and
  evaluates `bucket_name != ""`. Severity `"error"` means the build aborts if the bucket name is empty.
- `generate.case "provider"` — dispatches on the resolved value of the `provider` variable.
- `aws { ... }` — arm selected when `provider = "aws"`. Contains Terraform HCL.
- `$bucket_name` in the code block — graydr variable, substituted before IaC processing.
- `${var.region}` in the code block — Terraform-native interpolation, passed through unchanged.
- `outputs { bucket_url = "${aws_s3_bucket.storage.bucket_regional_domain_name}" }` — output
  reference template. The resource type and attribute path are Terraform-specific.
- `azure { ... }` — arm selected when `provider = "azure"`. Contains Bicep HCL. Note that the
  `outputs.bucket_url` template string uses the Azure resource reference syntax instead of Terraform.

## Validating Your Module

```
graydr validate my_module.gmod
```

Exit code 0 means the module is structurally valid — all required blocks are present, input/output
declarations are well-formed, and validation rule syntax is correct. All errors are listed before the
compiler stops, so you see all problems in one pass.

`graydr validate` does not require a properties file or template. It checks structure only, not whether
all inputs are supplied (that check happens at `graydr compile` time).
