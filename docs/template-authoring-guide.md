# Template Authoring Guide

This guide explains how to write a `.gtpl` file — the assembly document that wires module instances
together into a deployable infrastructure configuration. Read it top-to-bottom to produce a working
template without consulting source code.

---

## Overview

A **template** is the assembly point for IaC resources. It declares which modules to instantiate,
supplies their inputs, and wires outputs from one module instance into inputs of another. The template
does not contain IaC code directly — that lives in modules. The template is the wiring diagram.

**Template vs. Module:**

| Concept    | Template (`.gtpl`)                        | Module (`.gmod`)                         |
|------------|-------------------------------------------|------------------------------------------|
| Purpose    | Wire module instances together            | Encapsulate provider-specific IaC code   |
| Contains   | Parameter groups, resource blocks, outputs | Interface, validation, generate/case blocks |
| Authored by| Platform engineer / infrastructure team   | Module author / library maintainer       |
| Executed   | Once per deployment target                | Once per resource instance               |

---

## Quickstart

Generate a starter template with:

```
graydr init template --output my_template.gtpl
```

This writes a valid `.gtpl` scaffold:

```hcl
# Generated by `graydr init template`
# See the Template Authoring Guide for complete documentation.
template "my_template" {
  metadata {
    description = "TODO: describe what this template does"
    version     = "0.1.0"
  }

  parameters {
    config {
      provider = {}
      region   = {}
    }
  }

  resource "main" {
    module = "my_module"
    inputs {
      my_variable = "$config.provider"
    }
  }

  outputs {
  }
}
```

Validate the file at any time with:

```
graydr validate my_template.gtpl
```

## File Structure

Every `.gtpl` file has the following top-level structure:

```hcl
template "name" {
  metadata    { ... }
  parameters  { ... }
  resource "instance_name" { ... }
  outputs     { ... }
}
```

The `template` keyword is followed by a string label — the template name. A template may declare
multiple `resource` blocks. The `parameters` block and `outputs` block each appear once.

---

## Metadata Block

Same structure as the module metadata block. At minimum, provide a `description`:

```hcl
metadata {
  description = "Minimal data platform template"
  version     = "0.1.0"
}
```

---

## Parameters Block

The parameters block declares the groups of configuration values that the template accepts as
external input. Each group is a named block containing key declarations:

```hcl
parameters {
  primary_db {
    provider = {}
    region   = {}
    size     = {}
  }
}
```

**How parameter groups work:**

- Each group name (`primary_db`) becomes a namespace prefix.
- Values inside the group (`provider`, `region`, `size`) are accessed in resource inputs as
  `$primary_db.provider`, `$primary_db.region`, `$primary_db.size`.
- The `{}` value for each key is a placeholder — the actual value comes from a properties file or
  a `-D` flag at compile time.

**Accessing parameter group values in resource inputs:**

```hcl
resource "main_storage" {
  module = "storage"
  inputs {
    bucket_name = "$primary_db.name"
    region      = "$primary_db.region"
  }
}
```

The dotted path `$primary_db.region` is resolved by the variable resolution chain at compile time.

---

## Resource Blocks

Each `resource` block instantiates a module. The block label is the **instance name** — it must be
unique within the template and is used in cross-resource output references.

```hcl
resource "main_storage" {
  module = "storage"
  inputs {
    bucket_name = "$primary_db.name"
    region      = "$primary_db.region"
  }
}
```

Fields:

| Field    | Description                                                        |
|----------|--------------------------------------------------------------------|
| `module` | The name of the `.gmod` module to instantiate (looked up in `--include-path`) |
| `inputs` | Key-value map supplying values for the module's declared inputs    |

Input values can be:
- **Variable references:** `"$group.key"` or `"$key"` — resolved from the variable resolution chain.
- **Literals:** `"us-east-1"` — a fixed string value.
- **Output references:** `"${other_resource.output_name}"` — resolved from another resource's output.

---

## Cross-Resource Output References

When resource B needs a value produced by resource A, use an output reference in the inputs block:

```hcl
inputs {
  endpoint = "${resource_a.bucket_url}"
}
```

The `${resource_a.bucket_url}` syntax tells graydr: "take the `bucket_url` output from the resource
instance named `resource_a` and inject it here."

**Complete before-and-after example:**

Resource A (`main_storage`) uses the `storage` module, which declares `bucket_url` as an output:

```hcl
resource "main_storage" {
  module = "storage"
  inputs {
    bucket_name = "$primary_db.name"
    region      = "$primary_db.region"
  }
}
```

Resource B (`app_server`) consumes `main_storage`'s `bucket_url` output:

```hcl
resource "app_server" {
  module = "appserver"
  inputs {
    storage_endpoint = "${main_storage.bucket_url}"
  }
}
```

At compile time, graydr resolves the dependency graph automatically: `main_storage` is compiled
before `app_server` because `app_server` depends on `main_storage`'s output. The template author
does not need to declare an ordering — the compiler infers it from the `${...}` reference.

**Dependency graph resolution:** The compiler builds a directed graph where each `${resource.output}`
reference creates an edge from the consumer to the producer. Resources are emitted in topological
order. If a cycle exists (A depends on B, B depends on A), compilation fails with `CircularDependency`.

---

## Explicit depends_on

When resource B must be deployed after resource A but does not consume any of A's outputs, declare
the dependency explicitly:

```hcl
resource "app_server" {
  module = "appserver"
  inputs {
    region = "$primary_db.region"
  }
  depends_on = ["main_storage"]
}
```

`depends_on` accepts a list of resource instance names. The compiler ensures these resources are
emitted before the declaring resource, even without an output reference.

Use `depends_on` for:
- Resources that share a network namespace and must be created in order.
- Resources where a later resource's initialization requires a prior resource to exist.

---

## Template Outputs

The template-level `outputs` block exposes values from resource instances as the template's public
interface. Downstream consumers (or the operator) can inspect these values after compilation.

```hcl
outputs {
  storage_url = "${main_storage.bucket_url}"
}
```

Output values use the same `${resource_instance.output_name}` reference syntax as cross-resource
inputs.

## Properties Files

Parameter group values are supplied at compile time via properties files. graydr supports both YAML
and JSON.

**YAML properties file (`sample.props.yaml`):**

```yaml
primary_db:
  size: XL
  region: us-east-1
  engine: postgres
provider: aws
environment: production
```

Dotted variable access: `$primary_db.size` resolves to `XL`. `$provider` resolves to `aws`.

**Deep-merge with multiple properties files:**

```
graydr compile \
  --template my.gtpl \
  --include-path ./modules \
  --properties base.yaml \
  --properties env-override.yaml
```

Properties files are deep-merged in declaration order. Later files take precedence for duplicate keys.
This allows a base configuration file and an environment-specific override.

**CLI override on top:**

```
graydr compile \
  --template my.gtpl \
  --include-path ./modules \
  --properties base.yaml \
  -D primary_db.size=XXL \
  -D provider=azure
```

`-D key=value` overrides are applied on top of all properties files. Multiple `-D` flags are allowed;
if the same key is provided twice, the last value wins.

**Full variable resolution priority (lowest to highest):**

1. Module `default =` in `interface.inputs` declaration
2. Template `inputs { key = "literal" }` in the resource block
3. Properties files (YAML/JSON, deep-merged in declaration order)
4. `-D` flags (repeatable, last value for a given key wins)

Any variable reference that cannot be resolved from these four sources is a **hard compile error**.
There is no fallback and no null — missing = fail.

## Complete Example

The following is `tests/fixtures/sample.gtpl` — the canonical reference template used throughout the
test suite.

```hcl
template "data-platform" {
  metadata {
    description = "Minimal data platform template"
    version     = "0.1.0"
  }

  parameters {
    primary_db {
      provider = {}
      region   = {}
      size     = {}
    }
  }

  resource "main_storage" {
    module = "storage"
    inputs {
      bucket_name = "$primary_db.name"
      region      = "$primary_db.region"
    }
  }

  outputs {
    storage_url = "${main_storage.bucket_url}"
  }
}
```

Annotations:

- `template "data-platform"` — the template name.
- `parameters.primary_db` — a parameter group named `primary_db` with three keys: `provider`,
  `region`, `size`. Values come from properties files or `-D` flags.
- `resource "main_storage"` — instantiates the `storage` module with instance name `main_storage`.
- `inputs.bucket_name = "$primary_db.name"` — resolved from the `primary_db.name` properties key.
- `inputs.region = "$primary_db.region"` — resolved from `primary_db.region`.
- `outputs.storage_url = "${main_storage.bucket_url}"` — exposes the `bucket_url` output from the
  `main_storage` resource instance as the template's public `storage_url` output.

## Compiling Your Template

```
graydr compile \
  --template my.gtpl \
  --include-path ./modules \
  --properties env.yaml
```

Flags:

| Flag                     | Description                                                       |
|--------------------------|-------------------------------------------------------------------|
| `--template <PATH>`      | Path to the `.gtpl` file                                          |
| `--include-path <PATH>`  | Directory to search for `.gmod` and `.gfrag` files                |
| `--properties <FILE>`    | Properties file (repeatable; later files take precedence)         |
| `-D <KEY=VALUE>`         | Override variable (repeatable; last value wins)                   |
| `--output <FILE>`        | Write compiled output to file (default: stdout)                   |

Exit codes: `0` = success, `1` = any error (parse error, missing variable, no matching arm, etc.)
